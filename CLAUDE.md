# DAOTurnBased -- project context

Turn-based combat for Dragon Age: Origins, as a native plugin (`turnbased.dll`) on DAOLib, the loader and library in `extern/DAOLib`. `dev/DESIGN.md` is what the mod does and why. `dev/UI.md` is the turn bar and movement preview, made of the game's own Scaleform UI once DAOLib reaches it. `dev/DAOLIB_NEEDS.md` is what the mod needs from DAOLib, kept current as the mod grows: it is DAOLib's work list, and the DAOLib session reads it. `dev/TESTING.md` is how to test in play and what the log says.

Markdown here is not hard-wrapped: one line per paragraph or list item.

Licensed GPLv3 (`LICENSE`, the user's choice, 2026-09-30). `src/plugin/EluvianAPI.h` is Eluvian's header, MIT, as its own notice says.

## The target

DAOLib's `CLAUDE.md` has the game, the one exe build every address is from, the toolchain and where logs go. Everything is 32-bit x86; `CMakeLists.txt` refuses a 64-bit configure.

## DAOLib is an extern

`extern/DAOLib` is a git submodule (DAOLib's own repository), built with this one through `add_subdirectory(... EXCLUDE_FROM_ALL)`, which gives `DAOLib::daolib` and `add_daolib_plugin`: the way Skyrim plugins build CommonLibSSE. DAOLib's dependencies come through this repository's `vcpkg.json`.

- After cloning: `git submodule update --init --recursive` (DAOLib has a submodule of its own, `extern/DAOAddressLibrary`, since `8b027c6`).
- Since DAOLib `8b027c6` (2026-10-01) the game's addresses are IDs, looked up at run time in a file for the running build of the game: the same dll runs in GOG's game and EA's. The build packs those files into `build\<preset>\daolib\addresses` (daolib depends on them itself) and `tools/deploy.ps1` copies them to `bin_ship\daolib\addresses`; without the one for the running exe the loader loads nothing. The mod has no address of its own: what it hooks and whom it takes a command's caller for are DAOLib's IDs (`src/game/Gate.cpp`). It has run in GOG's game only. The plugin API is 2: the loader and every plugin in the game's folder must be of the same API, so a deploy across that line is agreed with the other plugins' sessions (Eluvian's) first.
- Since DAOLib's issue 26 (on its master as `b8bbe63`; the mod was built on its branch for it, `f442300` and then `d892f71` for what the mod met, commits no branch of DAOLib's has now; issue 47 here, 2026-10-05) a plugin is a folder of its own: the loader loads `bin_ship\daolib\plugins\turnbased\turnbased.dll` and no dll loose in `plugins\` (its log says where one belongs), and the turn bar's movie is served to the game from beside the dll (`turnorder.swf` there, by `add_daolib_plugin`'s `FILES`), so nothing of the mod's goes into `packages\core\override\`. `tools/deploy.ps1` copies the folder and takes out what earlier deploys left: the loose dll and pdb, the override's `turnorder.swf`, which the game's resource system would find before the plugin's own, and the two material objects of 2026-10-01 there. The API is still 2, but the loader and every plugin in the game's folder change layout in the same restart, so a deploy across this line too is agreed with the other plugins' sessions first. ## Layout

```
src/core/     the rules and the turn state machine: no <Windows.h>, no DAOLib, no dao:: type. Tested.
src/game/     every call into the engine, through DAOLib: Bridge (observe, apply), Gate (the hooks),
              Bar (the turn bar's calls, screen and portraits), Preview (the path to the cursor), Camera,
              SettingsFile, CoSave (the mod's file in each save), TacticsBox (the box on the game's
              tactics page). Verified by playing.
src/plugin/   DAOLib_Load and the frame callback that runs the machine
ui/turnorder/ the turn bar's movie, ActionScript 2 (frame_1/DoAction.as)
ui/tactics/   the tactics page's box's movie, the same, loaded into the game's tactics screen
tests/        Catch2 over src/core: scripted cases in a stand-in for the game (World.h), and random
              fights checked against the design's promises every frame (test_fights.cpp)
tools/        build.ps1 (DAOLib's, for this tree), deploy.ps1, mutants.py (break the core on purpose),
              movie.py (build ui/ into build\ui: turnorder.swf and turnbased_tactics.swf), snapshot.ps1
              (look at one in Ruffle), reticles.py (the preview's red ring and marker, made from the
              game's own files into build\art),
              sweep.py (who is in a fight, swept through an area by Eluvian: it launches the game),
              portraits.py (every appearance's portrait on contact sheets, each a real creature in the
              running game: how a row of src/core/PortraitTable.h is found and checked by eye),
              test_*.py, console.ps1, check-powershell.ps1
dev/          design, UI, DAOLib's needs, testing; images/ for the docs
extern/DAOLib the submodule
```

**The movies** (two since issue 46: the turn bar's and the tactics page's box's) are built outside CMake, since it needs Java and FFDec: `python tools\movie.py` writes each a SWF shell and has JPEXS FFDec (`C:\Modding\ffdec_26.3.0`, runs on the installed JDK) compile its ActionScript into it. `.\tools\snapshot.ps1` plays one in Ruffle (`C:\Modding\ruffle_2026_09_30`), which shows the turn bar's sample fight (or, with `-Movie build\ui\turnbased_tactics.swf -Width 1024 -Height 768`, the tactics box on a stand-in of its screen's bottom row), and saves a PNG. Both tools were installed 2026-09-30 at the user's go-ahead ("install it as needed"). `dev/UI.md` has how the movie talks to the plugin and to the game.

**The red ring and the red marker** (issue 72) are built outside CMake too, since they are made from the game's own files and are not in the repository (the art is the game's): `python tools\reticles.py` reads the game's archives (`DAO_GAME_DIR` or `--game` for a game elsewhere than GOG's folder) and writes twenty files into `build\art`: six textures (the party's ring in gold and in red for the path's marks, and the movement marker in red), six material objects naming them, seven models naming those, and `vfx_base_turnbased.gda`, three rows of the visual effects' table (1,000,000 to 1,000,002) naming the models, which `src/game/Preview.cpp` places: the marks along a path, gold and then red, and the red marker at an end past the movement left. The marks' ring has its band twice as wide as the game's art has it (`BAND` in the tool, a constant: at the art's own width a mark's band is under a pixel, thin and faint). Pure Python, no tool to install; it stops with nothing written where a file of the game's is not as it was read. `dev/UI.md`, "The red ring and the red marker", has what each file is, how the red was measured and how the band is widened. Without them in the game the mod says so at start and draws a path as the movie's line.

**The one architectural rule: `src/core` never includes `<Windows.h>`, links DAOLib or names a `dao::` type.** The machine takes what `src/game` observed and answers with effects for `src/game` to apply; `src/game/Bridge.cpp`'s `static_assert`s keep core's numbers (game modes, command types, the invalid object) equal to DAOLib's. Anything that can be decided without the game belongs in core, with a test.

The machine is not thread-safe by itself: `src/plugin/Plugin.cpp` holds a mutex over every call into it, and never holds it while calling the engine, since applying an effect (an AI told to choose) can queue a command that comes back through the gate.

**Every line of the mod's own logic earns its keep, and what a change makes unnecessary is removed in that change.** The user's rule, said four times before it was written here (2026-10-06: "if we're going to implement our own thing, it better be something the engine doesn't already handle. Every line of code we add must earn its keep"; 2026-10-09: "All the custom logic that goes into our code base needs to earn its keep. If new logic obsoletes old logic, remove old logic"). Start from the simplest rule, on the engine's own present word wherever it has one. A special case (a timer, a latch, a state remembered against what the engine says now, a second reading of the same thing) stays only if a test fails without it and a sentence in `dev/DESIGN.md` says what it buys; one that guards against another of the mod's own mechanisms is a sign that mechanism is wrong. Old logic kept beside the new that replaces it, as an input, a fallback or "to be safe", is not kept: it goes, with its tests and its mutants, in the same branch. This is not a question to bring to the user each time; only their own design choices (their settings, their stated rules) are theirs to change.

## Building

```powershell
.\tools\build.ps1 -Preset core -Test            # src/core and its tests only: the fast loop, no DAOLib
.\tools\build.ps1 -Preset debug -Test           # turnbased.dll, DAOLib's loader, the tests
.\tools\build.ps1 -Preset debug -Format -Lint   # formatters, then clang-tidy, ruff and PSScriptAnalyzer
.\tools\deploy.ps1                              # into the game (closed); -Remove takes the plugin out
.\tools\build.ps1 -Preset release -Test         # optimised, with its pdb: the build to play on
.\tools\deploy.ps1 -Preset release
```

**The game is played on the `release` preset** (RelWithDebInfo; issue 54, 2026-10-05), and the gate stays on the debug ones. A debug `free` validates its pointer under the process heap's lock, which every plugin shares: three stalls of five to seven seconds in one day's play had the frame thread waiting there (DAOLib's hang logs), once inside the mod's own `operator delete`. The pdb is kept, so a crash or hang log still names the mod's frames. Eluvian's session plays on its optimised build too; a debug plugin beside it brings the checks back for both.

`-Test` runs the tests as many at a time as the build's jobs (`ctest --parallel`, since 2026-10-03: each test is a process of its own with nothing shared; 20 s became 8), as the mutants run side by side.

`build\debug\` is a game folder's worth of files: `version.dll` (DAOLib's loader), `daolib\addresses` and the plugin's folder `daolib\plugins\turnbased\` (`turnbased.dll`, its pdb, the movies, `turnorder.swf` and `turnbased_tactics.swf`, and in its `override\` subfolder the twenty files of the preview's rings and red marker; a loose `daolib\plugins\turnbased.dll` until 2026-10-05). A movie is copied there from `build\ui`, and the red ring's files into the subfolder from `build\art`, on every build, whether the dll links or not (the target `turnbased_files`, DAOLib's `FILES` and `OVERRIDE`; one not made yet warns and is skipped), so the order is `python tools\movie.py` and `python tools\reticles.py`, a build, the deploy: `tools\deploy.ps1` copies the folder as the build left it, subfolder and all, stops at a movie built since the last build, says so where the rings' files are not in the subfolder, takes out of the game's subfolder any file the build has not, and any of the game's kinds of file loose beside the dll (where issue 72's first build had them, and where nothing reads them). The format and lint targets are DAOLib's `cmake/Quality.cmake` run over this tree, with this tree's `.clang-format` and `.clang-tidy` (DAOLib's, copied); they are the plugin presets', since they read its compile database. The core presets (`core`, `core-asan`, `core-cov`) build `src/core` and `tests` alone, as SkyrimFollowerTactics' do. `core-cov` is 64-bit with clang-cl, since LLVM ships the coverage runtime for x64 only, and fetches Catch2 rather than use vcpkg's x86 one.

## Before every commit

```powershell
.\tools\build.ps1 -Preset debug -Test -Format -Lint
```

That is all a commit on a feature branch needs (`-Preset core -Test` is the faster loop while the work is in the core). The rest is the merge's (the user, 2026-10-09: "We should only run them when ready to merge to master. If we find an issue later in dev, we can just fix it on the dev branch. We squash before merging to master anyway"; until then the whole of it ran before every commit, and three branches gated side by side kept the machine at full load for a night).

## Before a merge to master

Once, on the squashed commit that will merge:

```powershell
.\tools\build.ps1 -Preset debug -Test -Format -Lint
.\tools\build.ps1 -Preset debug-asan -Test
.\tools\build.ps1 -Preset debug-analyze
```

## Writing files from the shell

The Bash tool turns `\\` into `\` and `\t`, `\b` into control characters inside a heredoc, so a path like `.\tools\build.ps1` written through one comes out broken (it happened twice, 2026-09-30). Write anything with a backslash through the Edit or Write tools.

## Style

As DAOLib's: clang-format's stock Microsoft style, `/W4 /WX`, and lint for correctness, cost and readability, the tests included (issue 55; the user, 2026-10-05: "style & readability also matter. We want to write good clean code, avoid complexity"). `.clang-tidy` is this tree's own list: `readability-*` and `modernize-*` are on less the checks that are taste alone, each left out with its reason in the file. Most of them can rewrite what they find; the diff is read line by line (a fix has been wrong twice: `!(a == b && c)` came back as `!a == b || !c`, and a comparison that passed over a distance that is no number came back as a `std::min` that took it). Comments say why and what was read, with dates and where, not what the code does. A file's head says what it is for and how it fits. Aggregates are initialised whole or through a maker (`Effect::Of`), since clang-tidy fails a partial one.
