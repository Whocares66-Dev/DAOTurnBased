# What the turn-based mod needs from DAOLib

Written while building the mod (2026-09-30), for DAOLib's work list. Each item: what the mod wants it for, what is already known (leads read while building this: addresses, class names, strings), what the mod does meanwhile, and how a session in play would show it works. Most urgent first within each section.

## Already done

- **DAOLib as an extern.** Built into this repository from the `extern/DAOLib` submodule through `add_subdirectory` and `add_daolib_plugin`, as Skyrim plugins build CommonLibSSE: DAOLib `eb20478`, "DAOLib can be built inside a plugin's own repository".
- **The command's layout** (was "The command queue", item 3): DAOLib `9b9e067`, read from the script constructors, not yet checked in play. `dao::Command` has `Target()`, `Position()`, `Ability()`, `Static()`, `PlayerIssued()` and its parameters. Types 39 (sheathe or draw) and 41 (turn) are named, and the mod now counts both as free. `DestroyStructure(Command)` returns a command to the pool `AddCommand` itself uses (0x0066DE30), which settles the freeing of a refused script command. The mod does not use the fields yet. They are what the reach check needs (below, "The world under the cursor", item 4).
- **The command queue** (was its items 1, 2 and 4): DAOLib `b660e43`. The queue always takes a command it is given and no caller frees one after, so the gate frees every command it refuses, whoever queued it. The player's orders carry `Command::PlayerIssued`, which the gate now reads for the source instead of guessing from return addresses; the ten callers are named in DAOLib's `Addresses.h`, and the gate warns of any other. `CCObject::CurrentCommand`, `CommandAt` and `CommandQueueSize` read the queue directly; the mod still asks through the script commands (a later change). All 43 command types are named from `commands.gda`, and the mod's core has them all, checked against DAOLib's at compile time.
- **The GDA string and bool getters** (was the UI's item 6): DAOLib `0516b73`, with each table's rows and columns.
- **Sending a message as the engine does** (was the camera's item): DAOLib `c6a0810` and `bc5e718`, `dao::messages::Send`. The camera's follow now sends a `CenterOnObjectMessage` to the current mode through it (`src/game/Camera.cpp`); the registry looks through base classes, so combat mode takes it. Still off by default until seen in play.
- **Calling into a movie** (was the UI's item 2): DAOLib `8c6b9d7` and `d74b27c`: `dao::gui::Movie`'s `SetVariable`, arrays and `Invoke`, and the game's movies found by name. The turn bar pulls instead for now (`dev/UI.md`, "The protocol"), since which thread a movie may be called on is not known.
- **Melee reach** (was "The world under the cursor", item 4): not needed from DAOLib after all. The mod works it out from the scripts' own rule and the data tables (`PerSpace`, `Range`) through `dao::gda` and `Command::Target` (`src/core/Rules.h`, `Reach`; `src/game/Gate.cpp`, `WalkToTarget`).
- **Hearing a movie** (was the UI's item 3): DAOLib `fd3bd7f`, `dao/Gui.h`: `OnFSCommand`, `OnExternalInterface`, answering with `Value`s. The turn bar's clicks (end turn, focus a portrait) and its questions (the cards) can come this way once a movie can be shown.
- **A portrait of any creature** (was the UI's item 3, the user's priority for enemies): DAOLib `ce27567`, `CCCreature::RenderPortrait()` and `PortraitImage()`, through the engine's own `CCCreature::UpdatePortrait`. The turn bar renders one per combatant the game has none for, one per view published, once per fight, and uses the creature's existing one when it has one (`src/core/Portraits.h`, `src/game/Bar.cpp`; `dev/UI.md`, "Portraits"). Checks 15 to 17 below. No leak: `CCCreature::~CCCreature` (0x006BAFE0) destroys the renderer at `+0x78C` (0x007F3D00) and frees it (DAOLib session, 2026-09-30), so an enemy's lives as long as the creature, a corpse's until the area unloads. Nothing frees one early on purpose: a movie may still be showing its `img://` name.

## Checks in play the mod depends on now

Things the mod already relies on that DAOLib has read but not seen work. `dev/TESTING.md` here says what the mod's log will show about each. Worth folding into the probe or the example plugin, and into `dev/LIBRARY.md`'s table, once seen.

**Seen in the first session in play** (2026-09-30, 09:28, a fight of seven at Highever, four rounds): checks 2, 9, 11 and 13 hold, and 8 has its answer, each marked below. A turn-based fight ran whole: turns in initiative order, enemies acting on theirs, an AI cut off at its movement with its action kept, the pause key ending turns. At 09:41 the turn bar's screen was added and its movie found as `turnorder.swf` in the override folder, and at 09:54 it was shown over the fight, placed and drawn as designed, in the game's fonts (UI item 1). DAOLib's own session saw the player-issued flag on every order and on none of 84 AI commands, and the movies' calls on the scripts' thread.

1. **Refusing a command at `CCObject::QueueCommand`** (return 0 without calling the original), and freeing it with `dao::script::DestroyStructure(Command, ...)`, for every caller (DAOLib's reading: no caller frees one after). To check: the engine, the scripts and the player's clicks live with a refusal, and the freeing is right. A double free would crash soon, a leak would show as memory growth over a long fight.
2. **Seen working.** **`SignalEvent` with `bProcessImmediate` from the frame callback.** An AI's turn starts with a synthetic `EVENT_TYPE_COMMAND_COMPLETE` signalled this way (`src/game/Bridge.cpp`, `Poke`). To check: the creature's script runs inside the call, while the game is paused, and its `AddCommand` arrives at the queue before `SignalEvent` returns.
3. **`CClientExoApp::SetPaused(paused, second = true)` from the frame callback**, many times a fight. What `second` means is still open (DAOLib's `dev/TURN_BASED.md`); the mod passes what the pause key does.
4. **`SetPrimaryControlled`** as a way to select the party member whose turn it is: whether it selects as the portrait click does, moves the camera, or does something else.
5. **`ClearAllCommands(creature, 1)`** on a creature mid-attack, mid-walk and knocked down: that it stops it at once, and what it does to a knockdown's recovery.
6. **Intercepting `ToggleGamePause` without proceeding**, popping its one int. `ScriptHooks.h` documents the pattern; nothing has used it in play.
7. **`IsMoving` and `GetPosition` every frame**: that `IsMoving` is true for a creature walking under its own command, and false for one pushed by an effect.
8. **Answered: the wrong property.** `PROPERTY_ATTRIBUTE_MOVEMENT_SPEED_MODIFIER` read 60 for every creature in the first session. The scripts' header gives it id 20, and row 20 of the shipped `properties` table is `Flanking_Angle` (0 to 180). The table has no movement speed at all. The mod now takes a creature's pace from its appearance's `Game_CbtSpeed` (`src/core/Rules.h`, `SpeedFactor`); Haste and slows wait on the effects item below. Worth a comment beside the constant in DAOLib's generated `ScriptConstants.h`: other `PROPERTY_*` ids may be as stale.
9. **Seen: it does.** Eleanor's move and Dog's ability were queued while paused, with no fallback. The fallback ran the world only for clicks that queue nothing (a refused order, an ability picked before its target), so it is now off by default (`[turns] order_run_ms = 0`). **An order given while paused reaching `QueueCommand` at once.** The mod assumes it does, and falls back to running the game for a moment if it does not (`Phase::Dispatching`; the log says `an order but no command while paused`). Which it is decides whether the fallback is a rarity or the normal path.
10. **Explore mode's order handlers watched by detour** (`src/game/Gate.cpp`, `OrderWatch`): ten of them, called through unchanged. Their `ret 4` is confirmed for all ten in `MessageHandlers.h`.
11. **Seen working** (DAOLib's eighth session, and `from player` on every order here). **`Command::PlayerIssued`** on the player's clicks, quickbar and steering, and on nothing else: the log's `from player` on every order in a session, and `from engine` never on one.
12. **Half seen**: DAOLib's example sent one to explore mode, and it was handled (09:42, the player's creature). Combat mode, which the mod sends to, is still to see. **`dao::messages::Send` of a `CenterOnObjectMessage`** to the current mode, with `camera_follow = true`: the camera goes to whoever's turn it is.
13. **Seen: on the scripts' thread.** **Which thread the player's orders reach the queue on.** The reach check calls script commands, so it runs only on the scripts' thread; the log's first `the player's orders reach the queue on (or off) the scripts' thread` says whether it can run at all. Off, it needs the distance and the tables read without the VM (the object's position; `dao::gda` needs no VM already).
14. **Seen working** (10:22): Teyrna Eleanor with a mace (base item 4) refused at 15.4 m, reach 3.5 m, 11.9 m to walk with 9 m left, the weapon read as the game has it. A bow's 45 m and a big target's reach are still to see. **The reach check against the game's own**: a click on an enemy the AI would call in reach (3.5 m plus half its personal space) is let through, one past it is "Too far". `GetDistanceBetween` is taken to measure centre to centre, as the AI's check uses it.
15. **Seen working** (10:04, `dev/images/turnorder-ingame.jpg` here): enemies' portraits rendered with the world paused draw as the party's do, framed and lit by the game's portrait camera. Before that: at 09:54, with the world paused, the turn bar rendered four of Howe's men a tenth of a second apart (`img://portrait_bhn200cr_howe_landra43`, the tag and a counter), no crash, no hitch reported. The cards showed grey: the movie left `.dds` off the names, which the game's own movies add (fixed). The picture itself is still to see. **`RenderPortrait()` from the frame callback, with the world paused** (a turn-based fight holds it paused): that the texture is drawn by the time the movie loads it, not blank or black until the game runs. The log names each portrait (`Genlock's portrait: img://portrait_12 (rendered)`), and the turn bar shows it or not.
16. **What a render costs.** The engine clones the creature's model for its renderer. Ten enemies at a fight's start are rendered one per tenth of a second. A hitch then, or none, is worth knowing, and a timing per render would say more (a DAOLib trace).
17. **Seen working**: the party's came from `PortraitImage()` with no render (`portrait_player0`, `portrait_gen00fl_dog1`, `portrait_bhn100cr_mother2`). **`PortraitImage()` on a party member** gives the same image the party bar shows (the data tree's `Party.Members.N.Portrait`), with no render. The turn bar takes it first and falls back to the data tree in the movie.

## The command queue

1. **The top byte of the command's first word**, not read yet (the rest of the layout is done, above).
2. **An event when a command starts and when it ends**, for any creature. `COMMAND_COMPLETE` reaches `OnScriptEvent` only sometimes (DAOLib's `dev/LIBRARY.md`, the fifth session). The mod polls instead: busy for two frames running means done.

## The UI (`dev/UI.md`)

The turn order bar, the movement preview and the on/off switch are made of the game's own Scaleform UI. The bar's side is read now (above), not yet seen in play. In order of need:

**The user's ask of 2026-10-01, first here: a "Turn-based" section in the game's own settings.** "we should add a section, Turn-based, to the game settings. there toggle turn-based combat or not. not just hotkey." Today the switch is a key (Ctrl+T), a line of `turnbased.ini` and a test tool. Wanted: how the options screen is made (its movie, its tabs or sections, how the engine fills one and hears a control change, where it saves), and a way for a plugin to add a section of its own with controls: a section's name, and in it a checkbox to begin with ("Turn-based combat", bound to `[turnbased] enabled`); a slider and a choice of a few would carry the rest of the ini later (the AI's turn speed, who plays the party, the camera following). Each control wants a label, its value now, and a callback when the player changes it, on the game's thread; the mod keeps the value in its own ini, so the game need not save it. The switch may be refused (in a fight it cannot be changed), so a callback that can put the control back, or a way to grey it, would let the screen say so. If the game's screen cannot take a section, the next best is an entry in it that opens a movie of the mod's own. **Where** (the user, the same day, on lib-agent's finding that only the Controls tab's key list is built in script, the five tabs being fixed clips): "not controls, gameplay tab i think, its own section w/ a toggle". So the Game tab, a section headed "Turn-based" with the one toggle; the key's row stays with the keys, on the Controls tab.

1. **Load and show a movie of our own**: done as far as reading goes (DAOLib `da1c603`, `33636ba`: `AddScreen`, `ShowScreen`, `HasMovie`); the mod's `KeepScreen` uses them, and `tools/deploy.ps1` puts `turnorder.swf` in the override folder. What is left is seeing it in play, placed and layered like the game's (top centre, over the world, under menus), shown and hidden. Leads:
    - classes `GUI::ScaleformManager`, `GUI::ScaleformResourceFile`, `GFxLoader`, `GFxMovie`, `GFxLoadQueueEntryMT_LoadMovie`;
    - the movies' own `FSCommand:LoadMovie`;
    - where the game finds movies: `guiexport.erf`, and whether `packages\core\override` or an add-in's ERF is searched first.
    Wanted: `dao::gui::LoadMovie("turnorder.gfx", layer)` returning a handle, with `Show` and `Hide`.
2. **Publish data to the GUI's data tree** (lower now: the turn bar pulls its view through `TB_GetView` instead, `dev/UI.md`): the SmartData paths movies bind to (`GUI.SelectedChar.Attributes.7.Current`, `CORESTATS_HEALTHCURRENT`). If a plugin can publish `GUI.TurnBased.*`, a movie binds to it the way the party bar binds to health, with no polling.
3. **Extend the Options screen** (`optionsmenu.gfx`) with a turn-based switch, and learn where options are stored and read back.

## The world under the cursor, and drawing in it

For the movement preview (gold in reach, red too far):

1. **The cursor's point in the world, and the object under it.** Explore mode keeps them: `MoveCharacterToLocationMessage` has no fields (`dev/messages.csv`), so its handler (0x0070C9A0) reads the destination from `GameModeExplore`. `PreMoveCharacterToLocationMessage` (0x0070AAF0) may run on the button going down. Wanted: `GameModeExplore::CursorWorldPoint()`, `CursorObject()`.
2. **Done** (DAOLib `5b9b82f` `CurrentPath`, `8819b7c` `FindPath`, for an idle creature; the mod's `path_check`, not yet seen in play). **The pathfinder**: a path, and its length, from a creature to a point, as the creature would walk it. With it the preview draws the real path and the budget is exact before the move, not measured during it.
3. **Drawing in the world**: the ring area spells show while aimed (`ActivateAnalogTargetModeMessage`, `ActivateLinearTargetModeMessage` on explore mode), with a radius and a tint of ours. Otherwise, a visual effect placed at points along the path (`Engine_ApplyEffectAtLocation` with a VFX from `vfx_base`), which the script API reaches today, so it could be tried at once.

## The camera

1. **Follow a creature**, not only centre on it once: the camera keeping whoever acts in view while they walk. Centring is done (above); whether it follows on its own, or needs sending each frame, is to see in play.
2. **Smooth moves** (DAOLib `a24efda` to `6c26174`: `Camera()->Follow`, `SetFocusOffset`, `Scene()->SetYaw`, `Tactical()`; built on as `src/game/Camera.cpp`: a pan eased in the tactical view, the camera eased round behind a party member close in, enemies not followed close in. SetYaw seen in play. GetFacing's measure: facing = -(the forward vector's angle from +x) - 90 degrees, three creatures agreeing at 11:58, so behind is yaw = 90 - facing, not facing + 180 as first taken, which put the camera at the side; the mod uses GetOrientation's vector instead. The tactical pan still to see). **The user's request after the first fights (2026-09-30).** In the tactical view and over the shoulder, the camera snaps to each party member as the turn passes (`SetPrimaryControlled`) and to each enemy (`CenterOnObjectMessage`). Wanted: what explore and combat mode keep for the camera (its focus point and position), and either the engine's own smooth move to a point, if it has one, or a way to set the focus each frame so the mod can ease it there.
3. **What `CenterOnObjectMessage` does to a creature's AI.** Sent to combat mode on an enemy just before the mod's `COMMAND_COMPLETE` poke, it left every enemy choosing nothing on its turn, two fights running; with it off, they acted at once (10:09). The mod now centres after the AI has chosen, and in play (10:18) every enemy then acted and its action played out whole. What the handler does besides moving the camera is still worth knowing.
4. **Done, to see in play** (DAOLib `79d2baa`; the mod's `CameraDirector::Watch`). **A pan that stopped short at the hero's turn**, twice at `ai_turn_speed = 2` (play tests 2 and 5): the game's own pull toward the party (`CameraControllerExplore::PullToParty`), with no party member in view, moved the focus, and the pan took that for the player's and stopped. The player is now seen by the game's own pan function, the pull is held at rest while a pan runs, and `dao::camera::LastEnd` and `OnMoveEnded` say why a move ended. The mod logs the reason and pans once more if one ends short for anything but the player.

## Time and input

1. **Done** (DAOLib `1090803`, `GameModeExplore::RequestTarget`; the mod's `src/game/Targeting.cpp`, not yet seen in play). Found by DAOLib (5c34e31): `PerformAbilityMessage`'s handler never reads the message's target (0 from the quickbar is normal: seen in play 2026-09-30, 13:24). It uses the ability on the caster (self-only, a mode turned off), else the selected target (the global `0x00C06794`, set by the cycle-target keys and analog targeting) if valid, else the caster's attack target when the ability's `AutoTarget` column is set, and only failing all three asks (`BeginTargeting`, `0x0070BA30`). A character keeps its attack target from turn to turn, which is why a talent sometimes asks and sometimes does not. The mod's first try (intercept a message naming a target, send it again with none) could never act and was taken out. Now during a fight the quickbar's `PerformAbilityMessage` for the current creature's talent that is not for its user alone nor a mode is taken, and `RequestTarget` asks instead (`pick_targets`, on by default). **The player's talents go straight to the selected target.** With a target selected, a quickbar talent is used on it at once, where a turn-based player expects to pick the target (the user, 2026-09-30); a character keeps its target from turn to turn. Wanted either: a way to clear the selected target (explore mode's field, or the message that does it), which the mod would do at the start of each party turn; or `PerformAbilityOnTargetMessage` (the "ability on the selected target" handler, 0x00711A00) typed, so the mod can take it in a fight and send the plain ability message instead, which enters targeting.
2. **Done** (DAOLib `3c8cccf`/`4e0032e`, `dao::clock::SetSpeed`, seen in play at `23abbc1`; the mod's `ai_turn_speed`). **The game's time scale.** Fast AI turns. It scales the world's timer and the frame's, so logic, animation and sound together; the Flash UI keeps its own clock.
3. **Advancing game time without running the world**, if the engine allows it: effects and cooldowns would tick a round's worth between rounds, with no one standing idle on screen. Otherwise round padding stays "the world runs, nobody acts".
4. **Key bindings through the game's input map**: an action of our own (end turn, toggle turn-based) that the player rebinds in the game's controls screen. The GUI names `InputMappings.Mappings.ToggleFullPartySelect.PrimaryMappedKey` and kin. The mod polls `GetAsyncKeyState` meanwhile, and ends turns through the pause key's handler.

## Rules

**The user's two asks of 2026-09-30, late, before path on demand:**

- **Answered** (DAOLib `b51d676`, `dao::abilities::SetCooldown(creature, ability, remaining, total)` and `GetCooldown`; the mod's `Bridge::Apply`, not yet seen in play: that the slot draws the record's ratio is read from the record's side). **How the quickbar draws a cooldown, and setting it.** The user: the sweep on a quickbar slot should show turns, a third recovered with 2 of 3 turns left to wait. The mod holds a used ability with the script `SetCooldown(creature, ability, 3600)` and releases it with the seconds left, so the slot shows whatever 3600 s looks like. Wanted: what the sweep is computed from (the remaining time over the ability table's cooldown, over the value last set, or a ratio the engine pushes to the movie), where a creature's cooldown entry lives and its fields, and either which script calls give "remaining X of Y" or `dao::abilities::SetCooldown(creature, ability, remaining, of)` writing both, with a read of the same. The mod would set remaining/of to turns left over turns in all, on a scale real time cannot run out.
- **Done** (DAOLib `1d99f54`, `dao::world::RoomOf(object)->Shown()`; the mod's rule for who is in a fight, `src/game/Bridge.cpp`'s `Engaged`; the `seen` value not yet watched in play). A black room is one no party member has yet seen: the area marks the rooms the party stands in and some neighbours as in view, keeps them as seen, and hides the rest, their creatures inactive, even through an open door. It goes by the party, not the camera. **Whether a creature's room is drawn.** In Castle Cousland a fight took in nine enemies, most fighting guards rooms away, and the camera went to rooms that are black, not loaded or not drawn (the user's picture). The user does not want a distance rule; their idea is to leave out those in areas that are not loaded. The mod's first rule is sight and engagement from the scripts (`join_by_sight`, `dev/DESIGN.md`). Wanted: the engine's own answer, `dao::world::Drawn(object)` or `RoomVisible(object)`: what decides those rooms are black (the area's rooms or portals, from the party's place or the camera's), and whether that set follows the camera or the controlled creature. The mod would use it as the rule, or at the least not send the camera to a creature whose room is not drawn.

For what the design lists as later (`dev/DESIGN.md`, "Also needed"):

1. **A creature's movement rate effects.** Haste and slows are effects, `EFFECT_TYPE_MOVEMENT_RATE` (9) and `EFFECT_TYPE_MOVEMENT_RATE_DEBUFF` (11), each with its multiplier in the engine float `EFFECT_FLOAT_POTENCY` (1): 1.5 from `creature_core.nss`, 0.5 for the slows (`EffectModifyMovementSpeed`, `effects_h.nss`). The script `GetEffects` returns an array, which the generated wrappers do not take, and nothing reads an engine float. Wanted: the product of a creature's movement rate potencies, or better the rate the engine moves it at, if it keeps one. The movement budget multiplies by it.
2. **An effect's duration and remaining time** (`CGameEffect`), and **setting an ability's remaining cooldown** (`SetCooldown` exists as a script command; a direct read of the cooldown table would do). Needed to convert durations and cooldowns to rounds.
3. **An ability's kind**: modal or sustained, item use, and cast time. From `abi_base` through `dao::gda`, once someone confirms which columns mean what (`UseType`, `Speed`?). Needed for toggles and potions as a lesser action, and for action point costs.
4. **Leaving melee**: an event, or a cheap check, when a creature steps out of an enemy's melee ring (`GetCreaturesInMeleeRing`, `GetMeleeRingPosition`). Needed for opportunity attacks.
5. **Stealth at the start of a fight**, for a surprise round: `IsStealthy` is a script function over an effect; the effect's type would do.

## The library in general

1. **Plugin strings in the talk table.** The mod's floating text is English, in code. A plugin's own `.tlk`, loaded beside the game's (DAOLib's `tools/tlk.py` reads the format), would let it say things by string id in the player's language.
2. **Plugins sharing a hook.** DAOLib's probe and this mod both detour `QueueCommand` and the pause key's handler. Detours chains them, in load order. A note in `dev/PLUGINS.md` on what that means, or a shared dispatcher for the hot ones, would help as plugins multiply.
