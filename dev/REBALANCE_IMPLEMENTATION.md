# Rebalance implementation notes

Implementation on `rebalance-issue-1`, starting from the current specification at `ce28110`. `dev/REBALANCE.md` remains the design discussion. This file records code findings, completed slices, and integration issues; a tested core component is not a claim that the game uses it yet.

## First slice: turn-time accounting

`src/core/TurnTime.h/.cpp` implements capacity independently of elapsed clock time. Combat Tactics ranks alternate rollover and capacity; rollover extends capacity without extending the clock; pending work spends the next bar rather than enlarging it. `Spend` returns capacity paid and clock advancement, `Hold` consumes clock time through the fixed ratio, and `Finish` banks remaining capacity and advances only the clock's remaining share. Partial payments retain their fractional progress, so frame-by-frame movement does not lose time through repeated rounding. Only whole milliseconds can be spent or banked; a fractional capacity remainder below a millisecond is discarded at turn end, while the clock still advances its exact whole-turn total. Invalid zero turn duration becomes 1 ms and capacity addition saturates rather than overflowing.

This component is compiled into `tb_core` and exercised by `tests/test_turntime.cpp`. It is not yet wired into `TurnMachine` or the game bridge. The tests cover the proposal's two-turn cooldown/poison example, partial and whole holds, rollover on passing, multi-turn work, cancellation without refunding paid time, an interruption boundary, small movement payments, fractional holds, and extreme inputs. The interruption test supplies an event boundary; an event scheduler is not implemented by this class.

## Second slice: incremental action payment

`src/core/ActionTime.h/.cpp` carries an action's remaining cost over any number of turns. Each `Advance` pays only up to the supplied next timer boundary, action completion, or the turn's capacity. `TurnTime::CapacityUntilClock` converts that clock boundary through the fixed ratio, retaining fractional progress from earlier movement or holds. At a timer boundary the action enters `AwaitingEvent`; further payment and dispatch are refused until the caller applies that event and resolves interruption. An event simultaneous with completion is resolved before readiness. A dead or out-of-reach pending target is interrupted before advancing the new turn, releasing only unpaid cost. `TakeReady` grants dispatch once, after the caller's final validation, and cannot grant it while an event is unresolved.

`tests/test_actiontime.cpp` covers successive events, a lethal tick, simultaneous impact and interruption, a turn-boundary event, multi-turn work with changing capacity, an invalid pending target, zero-time events, fractional ratios, distant events, and one-time dispatch. These components do not own engine commands or resources. This is the payment state machine, not the engine event queue: the caller must supply the next due event and apply it outside the core before resolving it. Ending/passing a turn also needs chronological event processing; `TurnTime::Finish` is accounting only, not an instruction to batch engine callbacks without checking their outcomes.

## Third slice: the machine on a bar of time, behind a setting

`[turns] clock = time` (default `actions`, so nothing changes until it is chosen and seen in play). The machine's budget is `src/core/TurnBudget.h`: one action and meters as built, or a `TurnTime` bar that actions and walking both spend. The machine asks it the same questions either way (an action left, meters left, walked past them), so the rules that do not care which (who may act, when a walk is stopped, refunds, what a turn shows) are written once. What time mode does, in `TurnMachine`:

- **The bar**: `seconds_per_turn` (4), plus Combat Tactics' time (`TimeFromTactics`: a party member's own rank, `Combatant::tactics`; an enemy's or ally's by creature rank, `enemy_tactics = 0, 0, 2, 4, 4`), plus what the last turn rolled over, to the cap by the same rank. A lost or held turn rolls over nothing.
- **Walking** costs time at `pace` (4.66 m/s) times the creature's speed, after `free_step` (1 m) a turn; a move must fit or is "Too far", as built.
- **An action** costs its own time (`ActionCostMs`): `CommandRequest::actionSeconds` when the game layer gives it, else a stand-in by kind (a swing 2 s, a talent or a spell's cast 2 s plus its conjuring by `ConjureSeconds`, an item's drink 1.23 s, a mode turned off nothing). The `[turns] charge` list still overrides, as that many whole turns. `SwingSeconds` is the game's own formula (`CalculateAttackTiming`, `core_h.nss`) for the game layer to fill `actionSeconds` with.
- **An attack's walk is paid as it is let through** (`TurnBudget::Prepay`), then its swing, so the swing cannot leave the walk short; meters paid for and not walked stay walkable.
- **An action that does not fit** what is left (walk and swing together) is kept (`Verdict::Hold`, the existing `Charge` generalised with `owedMs`, its walk and its command type) when it is an attack or an ability not an item's; the next turn pays what it owes first, a whole turn at a time if need be, and the game layer gives it again (`ReleaseCast`), let through for nothing with its walk credited. An item's use that does not fit runs at once and owes the rest. A creature with an action kept walks no more that turn, not even its free meter.
- **The turn ends** when the bar is spent or its owner ends it; `end_turn_when_action_used` does not apply. **An AI with time left is told to choose again** after each action settles, up to `max_commands_per_turn`.
- **Cooldowns and effects' rounds** count in `seconds_per_turn` (`cooldown_seconds_per_turn` and `effect_seconds_per_round` stay the as-built settings). Per-creature clocks are not built: that needs DAOLib (below).
- **Initiative** adds `per_survival` (2) a rank of Survival (`Combatant::survival`), in both modes; the game layer does not read the rank yet, so it adds nothing in play until it does.
- **What the player sees**: `TurnView` carries the bar and what is left (`timed`, `timeMs`, `timeLeftMs`); the movement preview's gold and red split already follows `movementLeft`, which with time is what the bar would walk. The bar on screen is not built.

The random fights run in both modes (`test_fights.cpp`: 80 seeds each in the suite, 1,000 each in `[fights-long]`), with promises 4 and 5 as time has them: nobody walks further than the bar would walk as the turn began, and no action begins with no time left. They found two bugs on the way, each now a scripted case in `tests/test_time.cpp`: an AI's free meter walked after its action was kept, on into the next creature's turn (seed 130), and a turn ended by a kept action over a conversation then "resumed" for the next creature, a bug of the charge rule as built that kept actions made reachable (seed 594: `EndTurn` now clears the resume).

Not yet in the game layer (next): the gate's `HeldCast` keeps only abilities, so a kept attack is not given again in play; `actionSeconds` (the swing by weapon), `abilityType`, `conjureAnim` and `staff` are not filled; Combat Tactics' and Survival's ranks are not read; the bar is not drawn.

## Codebase map and issues found

1. **The existing machine is built around a different budget.** `TurnMachine::Budget` has one action, a separate movement maximum, and one failed-action refund. Cooldowns (`Hold`) and pending casts (`Charge`) store integer turns. `State`, the turn bar, previews, AI command limits, and `tests/World.h` consume that model. Replacing the budget alone would leave cooldowns, displays and AI inconsistent. Introduce the new state and observations together when the engine contract below exists.
2. **The available clock cannot implement the proposed creature clock.** `src/game/Bridge.cpp` applies `AgeTime` with `dao::clock::Advance(float)`. The DAOLib header at the branch pin `61e471e` (`src/dao/Clock.h`, read with `git show` from the main checkout submodule) documents a global effect/regeneration advance on subsequent updates, not a synchronous per-creature advance with ordered event callbacks. It explicitly excludes script `DelayEvent` timers and cooldowns. Advancing this once per actor would age everyone repeatedly. Requested capabilities are recorded in `dev/DAOLIB_NEEDS.md`.
3. **Queue acceptance is not a proven pre-impact boundary.** `Gate.cpp` hooks queueing; `ActorObservation` reports busy/moving/current-command state. The gate also subscribes to `dao::commands::OnEnd` and refunds known `DidNothing` failures through `OnCommandFailed`; that end event is useful but does not prove a pre-impact acceptance point. None of these observations proves that a command has been accepted but has not consumed resources or produced effects. The pinned `CommandEvents.h` does expose `OnStart` before a command runs, but explicitly forbids clearing or queueing commands from its callbacks. That observer is a probe lead, not a safe interception/commitment contract. The proposed start-then-pay sequence must be backed by a safe engine interception point; waiting a few frames cannot guarantee this for instant/modded abilities. Distinguish initial rejection (free) from failure after elapsed time was advanced (no rollback).
4. **Conjuring is still read incorrectly.** `Gate.cpp::DescribeAbility` treats `spellconjuringspeeds.Speed` as seconds. The proposal's research identifies loop counts and a separate animation start/loop duration, plus abilities without a conjure animation. Do not silently convert all rows using a guessed multiplier. Ask the engine for actual conjuring time and use explicit fallbacks only for unavailable timing data.
5. **Live action costs are not available yet.** `CommandRequest` carries cooldown and conjure seconds, not a verified full action duration, impact offsets, or resource commitment phase. Weapon swings, ability animations, archery, movement rate effects and creature-specific animations need observation before the cost rules can drive the gate.
6. **Area clock scheduling remains unspecified.** The proposal preserves area scripts and advances 4 s a round, but does not define when the shares run, how movement interleaves, or what a join/death does to the denominator. This must conserve the round total; it should not reuse the creature's capacity ratio blindly.
7. **Grabs and action-owned effects are an existing exception.** The machine currently advances the global clock while an actor executes an effect (for example Overwhelm), subtracting that time from the round allowance. Per-creature clocks must account for effects shared by attacker and victim before removing that workaround.
8. **Pending state needs generalisation.** Existing retained casts are ability-specific, and a released cast receives a fixed conjuring override in `Bridge.cpp`. A pending weapon attack or item needs its own retained-command lifetime, target validation and interruption rules. Unpaid cost is not extra turn capacity.
9. **The worktree's DAOLib submodule is not populated.** The first slice builds with the core preset, which needs no DAOLib. The headers above were verified read-only against this branch's pin `61e471e` using the main checkout's submodule object database, not a dependency upgrade on this branch. Initialise the pinned submodule or explicitly configure a chosen checkout before plugin integration; do not edit DAOLib here.

## Next implementation slices

- Establish command acceptance/commitment and scoped chronological clock capabilities in DAOLib; probe ordinary attacks, instant modes/items, a potion and a pending spell. No claim of safe pre-impact cancellation until observed.
- Connect the implemented action-payment state machine to an event scheduler that supplies the next deadline, applies the event, and checks interruption before continuing. End-turn, passing and hold-only spans need the same chronological delivery; decide rollover after relevant hold outcomes. The core deliberately does not invoke engine callbacks.
- Migrate the machine's observations, pending commands, cooldown/effect accounting, movement charging, AI and UI to the same budget. Keep a coherent old path until that integration can be enabled and tested end to end.
- Resolve the independent area-clock schedule, then test stationary exposure versus crossing an area, with joins and deaths during the round.
